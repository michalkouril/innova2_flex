# DDR4 memory controller: specification and choice

inn2f r2 includes a DDR4 controller (AMD MIG, `source/ip/ddr4_flex_ip/ddr4_flex/ddr4_flex.xci`). It calibrates
and refreshes the card's memory from power-on. Its AXI port is tied off, so the image stores nothing in DDR.

## Specification

| parameter | value |
|---|---|
| memory | on-board components, single rank, 1.2 V, Micron `MT40A1G16KNRD8B-075` |
| data width | **72 bits** (64 data + 8 ECC), ECC **on** |
| capacity | **8 GB** of data (`AxiAddressWidth` 33) |
| speed | **DDR4-2666**: tCK 750 ps (1333 MHz), CL 19, CWL 18, BL 8 |
| reference clock | 100 MHz differential, declared as 10000 ps |
| user interface | AXI4, 512-bit, 4-bit ID, 333 MHz `ui_clk`; read-priority arbitration, ROW_COLUMN_BANK mapping |
| extra clock | 100 MHz `addn_ui_clkout1`, which clocks the rest of the image |
| pinout | `source/constraints/ddr4_72bit_gen.xdc` (all nine byte lanes, generated by `gen_ddr_xdc.py`) |
| memory part file | `source/board/custom_parts_mt40a1g16knr075_dw8b.csv` |

## Why a DDR controller at all

The image does not need memory. The controller is there for two reasons:

* **Behaving like the vendor image.** Mellanox's Flex image trains the DDR and drives its 26 command/address
  pins. A Flex image with no controller drove none of them and ran about **5 °C cooler** than the vendor image. The
  running controller makes this image do the same work.
* **A DDR health signal.** The vendor image reports calibration at CR `0x020054` (1 = trained, 0 = not). This
  image reports the live `init_calib_complete` at the same address, so a host tool that grades a vendor card
  grades this one unchanged. A card with a defective DDR byte lane reads `0`. (The vendor's BIST registers are not
  implemented; see the README's feature table.)

## Why this configuration

* **72-bit with ECC:** the card has nine byte lanes wired to memory, and the vendor image trains all of them. A
  narrower controller would leave a lane untrained and its pins undriven.
* **DDR4-2666:** the `-075` speed grade of the devices. Measured on hardware (in a development design with the same
  controller settings): 8 GB byte-perfect at 2668 MT/s, and `ui_clk` measured against the host clock at
  333.47 MHz.
* **Reference clock declared as 10000 ps:** MIG only accepts a reference period from its legal list for each tCK,
  and 10000 ps is the one for 750 ps. The on-board oscillator measures 9996 ps, so the memory runs 0.04% fast
  (2668 rather than 2666 MT/s), well within the device's tolerance.

### The custom part file ("dw8b")

The devices are x16 parts. For a custom part with `Memory device width = 16`, MIG allows tCK no shorter than
833 ps (DDR4-2400), whatever speed the part declares. The CSV used here describes the same devices as x8:

* unchanged: every address dimension (row 16, column 10, bank group 2, bank 2), so MIG drives the same
  address/bank pins;
* changed: only `Memory device width` (16 → 8) and `Memory density`/`Component density` (16 Gb → 8 Gb), so the
  total still comes to 8 GB and `AxiAddressWidth` stays at 33.

With this file MIG accepts 750 ps and derives CL 19 / CWL 18. Do not use the other obvious rewrite (keep 16 Gb and
raise row to 17). It implies 16 GB, and MIG then asks for a 34-bit AXI address; the extra address bit would
alias.

## Things to know

* The `.xci` refers to the CSV by a **relative** path. See the README's build pitfalls: at the wrong depth Vivado
  silently uses a part without bank groups.
* `sys_rst` is driven low explicitly. The IP's default tie holds the controller in reset forever:
  `init_calib_complete` stays 0, `ui_clk` never starts, and nothing reports an error.
* Whether the ConnectX accepts a Flex image was **not** found to depend on the DDR settings (width, size, ECC) or on
  whether calibration succeeds. A card with defective DDR accepted the Flex image (the preceding build, same controller) and reports `0` at
  `0x020054`.
* AMD's generated controller output is not in this repository; the build regenerates it from the `.xci` (see
  README, Building from source).
